## 2. 加款标的与 `coin_type`

**余额一律进入用户的「WIN 充值余额」（`win_recharge_balance`）。**  
`coin_type` 仅用于管理端流水/统计区分币种类型，**不**再分流到 WIN-A 钱包。

账户标识为请求中的 EVM 地址；AIX 按小写匹配已注册用户。地址未注册返回 `2001` 且不加款。

| `coin_type` | 管理端标记 | 用户余额入账 |
|---|---|---|
| `1` | WIN | WIN 充值余额 |
| `2` | WIN-A | **仍为** WIN 充值余额 |
| `0` | — | **不支持**：返回 `2006`，明确未加款，贵方可退款 |
| 其它未开通值 | — | 同 `0`，返回 `2006` |

**缺省**：请求体**不传** `coin_type` 时，按 **`1`（WIN）** 记流水标记，余额入 WIN 充值钱包。

管理后台可配置当前开通的币种白名单；未开通的 `coin_type` 一律按不支持处理（`2006`）。用户端只展示 WIN，不做币种切换。

### 2.1 请求字段与签名

在贵方文档既有字段基础上增加：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `address` | string | 是 | `0x` + 40 位十六进制，大小写原样参与签名 |
| `amount` | string | 是 | 无符号十进制金额字符串 |
| `partner_id` | string | 是 | 合作方 ID |
| `timestamp` | number | 是 | 毫秒时间戳 |
| `nonce` | string | 是 | 幂等 / 防重放 |
| `sign` | string | 是 | HMAC-SHA256 签名 |
| `coin_type` | number | 否 | `0` / `1` / `2`；缺省按 `1`（WIN）记流水 |

**签名规则补充**：

- 若请求体**包含** `coin_type`（含显式传 `1`），则 `coin_type` **必须**参与签名，渲染为十进制整数字符串（如 `1`、`2`），与其它字段一起按贵方文档 §4 排序拼接。
- 若请求体**省略** `coin_type`，则签名字段集与旧版一致（不含该键），服务端按默认 `1`（WIN）记流水，余额入 WIN。

请求体示例（显式指定管理端标记为 WIN-A，余额仍入 WIN）：

```json
{
  "address": "0xAbC...",
  "amount": "100.5",
  "partner_id": "AIX10001",
  "timestamp": 1787875200455,
  "nonce": "c7d21be40a9f",
  "coin_type": 2,
  "sign": "..."
}
```

## 4. 限额

| 项 | 默认值 | 说明 |
|---|---|---|
| 单笔下限 | 10 | 管理后台可调，低于则 `2003` |
| 单笔上限 | 100,000 | 同上，超出则 `2004` |
| 单日上限 | 1,000,000 | 同上，超出则 `2005` |
| 调用频率 | 10 次/秒 | 超出返回 `5001`（明确未受理，可安全退款） |

**WIN 与 WIN-A 共用同一套限额**：单笔与单日累计均按加款金额加总计算，不按币种分别设上限。

> 因贵方文档明确不启用 IP 白名单，`secret_key` 是唯一准入凭证，我方额外按调用方 IP 做了一层基础限速（20 次/秒），防止未认证流量消耗资源。正常调用不会触发。

## 5. 行为确认（对应贵方文档 §2 的三条约定）

三条均已落实：

1. **`success = false` 一定没加款。** 加款事务提交成功后，即使后续步骤（写日志、签名等）出错，也一律返回 `true`。事务本身失败时返回 `5000`（结果不确定），不会返回 `false`，贵方按约定转人工核查而非自动退款。
2. **加款在单个数据库事务内完成**，「查用户 → 加余额 → 落流水」三步同事务，不会出现只加款不记账或只记账不加款。
3. **验签在 nonce 占用之前。** 顺序为：IP 限速 → 报文校验 → `partner_id` → 时间戳 → **验签** → 合作方限速 → **nonce 占用** → 格式与限额（含 `coin_type`）→ 加款。

**幂等**：同一 `partner_id + nonce` 只会成功受理一次，重复调用返回 `1004`。此外加款流水以 `partner:{partner_id}:{nonce}` 作为唯一键落库，即使去重记录被清理也不会重复加款。同一 nonce 不能改换 `coin_type` 再次加款。

**nonce 去重实现**：贵方文档建议 Redis `SET NX EX 300`，AIX 侧用 MySQL 唯一约束实现了等价语义（保留窗口同为 300 秒，不小于时间戳窗口）。选择数据库而非 Redis 是为了不引入新的运行时依赖，防重放效果一致。若贵方对实现方式有要求请提出。

**`aix_txn_id` 格式**：`AIXTX` + 8 位日期 + 8 位流水号，例如 `AIXTX2026082800000459`，全局唯一，建议贵方落库保存以便对账。

## 6. 响应签名规则（贵方文档未定义，此处补齐）

贵方文档 §4 的拼接规则建立在「值为原始标量」之上。请求体顶层字段均为标量，规则无歧义；但**响应体的 `data` 是嵌套对象，没有可直接拼接的原始值形态**，文档未定义该情况。

**AIX 侧采用的规则：只对顶层标量字段签名，`data` 不参与。**

即参与签名的字段固定为：`success`、`code`、`msg`、`timestamp`、`nonce`。排序、拼接、HMAC-SHA256、小写十六进制输出均与贵方文档 §4 完全一致。

补充两条渲染约定（文档同样未定义）：

- 布尔值 `success` 渲染为小写字面量 `true` / `false`
- 整数 `timestamp` 渲染为纯十进制数字串，无正号、无千分位

### 6.1 请用这两组数据对齐响应验签

与贵方文档 §4.1 同样的密钥：

```
secret_key = "aix_test_secret_key_0123456789ab"
```

**成功响应**（对应 §3 的成功示例）：

```
拼接串：code=0000&msg=success&nonce=c7d21be40a9f&success=true&timestamp=1787875200455
签名：  3e5b79bc5409928fed49d545d828c71b91ac77878973d6fc9c9fe4fe452c4155
```

注意该响应的 `data` 里含 `aix_txn_id`、`address`、`amount`、`credited_at`，但均**不参与**签名计算。

**失败响应**（地址未注册）：

```
拼接串：code=2001&msg=未找到该账户&nonce=c7d21be40a9f&success=false&timestamp=1787875200455
```

> 未注册地址返回 `msg=未找到该账户`。系统异常 / 结果不确定（如 `5000`、`5001`）时返回 `msg=系统更新中`。中文 `msg` 按文档 §4 第 3 条以原始 UTF-8 参与拼接，**不要**做 URL 编码。

以上成功向量由 AIX 侧实现实际计算得出，并已写入自动化测试固定。若贵方算出的结果不同，请在联调前告知，我方配合排查。


## 7. 建议联调顺序

1. **先对签名，两个方向都要对**：
   - 请求方向用贵方文档 §4.1 的向量（不含 `coin_type` 时与旧版一致）。若携带 `coin_type`，请将该字段按 §2.1 纳入拼接后再验签。
   - 响应方向用本文档 §6.1 的两组向量。
2. 故意错签 / 重放 nonce / 过期时间戳 → 应分别拿到 `1001` / `1004` / `1003`
3. 未注册地址 → `2001`，贵方侧确认退款链路
4. 已注册地址：
   - 不传 `coin_type` 或传 `1` / `2` → 余额均加到 **WIN** 充值余额（`2` 仅管理端流水标记为 WIN-A）
   - 传 `coin_type=0` 或未开通值 → `2006`
5. 限额边界（按金额合计，与币种标记无关）→ `2003` / `2004` / `2005`
6. 生产密钥切换演练（双钥并行）
